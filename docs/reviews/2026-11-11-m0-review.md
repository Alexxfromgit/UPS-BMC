## High

### R1 (high): `--redact-serial` still leaks the serial number via `iSerialNumber`
- **Where:** `apps/hid-probe/src/main.rs:191-195` (redaction) and `apps/hid-probe/src/main.rs:326-331` (string lookup). The fixture guidance is in `fixtures/README.md:5-6`.
- **What:** `--redact-serial` only drops `DeviceInfo::serial_number()`. `decode()` resolves every string-index usage through `get_indexed_string`, including Power Device `iSerialNumber` (0x84:0xFF, see `usages.rs:35`). It writes the result to `FieldValue.string` in both the console output and the JSON. The descriptor and payload hex are kept as well, so the index can be resolved again later. Battery System `SerialNumber` (0x85:0x86) is also emitted as a raw value.
- **Failure scenario:** HID UPSes commonly expose `UPS.PowerSummary.iSerialNumber` as a feature report. NUT's Eaton/MGE subdriver uses that path for `ups.serial`, but I haven't confirmed it for the 5E Gen2 descriptor. On Windows, running `hid-probe --redact-serial` prints `... iSerialNumber = 3 "G123A45678"` and saves it to JSON. Following `fixtures/README.md`, the user then commits that JSON to the repo.
- **Fix:** when `redact_serial` is set, skip `get_indexed_string` for 0x84:0xFF (or blank its `string`). Also replace the raw value of 0x85:0x86 with `None`, or leave it out. Add a unit test on `decode`/`FieldValue` that asserts no serial survives. You could also add `"redacted": true` to the JSON so curated fixtures are self-describing.

### R2 (high): arithmetic overflow in `add_fields`: panic in debug, a bogus field in release (**verified**)
- **Where:** `crates/ups-hid/src/descriptor.rs:371` (`*offset + n * g.report_size`), with saturation at `:386`.
- **What:** `report_size` and `report_count` are arbitrary 32-bit values from the descriptor. `n * report_size` and `offset + …` are unchecked `u32` arithmetic. Only the running total at `:386` saturates.
- **Failure scenario (reproduced):**
  - `05 84 09 30 77 00 00 00 80 95 03 81 02` (Report Size 0x8000_0000, Count 3) panics with "attempt to multiply with overflow" in debug builds. `cargo run -p hid-probe` (the README's command) is a debug build.
  - `05 84 09 30 77 FF FF FF FF 95 02 81 03 75 08 95 02 81 02` panics with "attempt to add with overflow" in debug. In release (no `overflow-checks`) it **silently wraps** and yields a data field at `bit_offset = 7`, `bit_size = 8`. `extract()` then decodes that field from real payload bytes, which is garbage presented as data.
  - The random fuzz loop hit this in 131 of 200,000 random descriptors (≤ 64 bytes). There were no other panic sites.
- **Fix:** use checked arithmetic. Either reject such descriptors with a new `ParseError::ReportTooLarge { offset }` or similar, or cap `report_size` at a sane maximum (for example 32, or 1024 if you want to keep wide fields). Then compute `bit_offset` with `checked_mul`/`checked_add` and fail on `None`. Add a regression test with the two byte strings above. Consider adding a `cargo fuzz` target, or a `proptest` "never panics" test, to CI.

## Medium

### R3 (medium): unbounded memory amplification from small descriptors (**verified**)
- **Where:** `crates/ups-hid/src/descriptor.rs:198` and `:356-383`.
- **What:** `MAX_RANGE_EXPANSION` (4096) caps the number of fields *per Main item*, but not overall. Globals persist, so each further 2-byte `Input` item adds up to 4,096 more `Field`s. Each `Field` also clones the whole `collection_path`, and nesting depth is unbounded.
- **Failure scenario (reproduced):**
  - A 4 KiB descriptor (the hidapi maximum) of `05 84 75 01 96 00 10` followed by `81 00` repeated parses into **8,372,224 fields (~638 MiB of `Field` structs, before heap paths)** in about 0.6 s.
  - A 2 KiB descriptor with 1,000 nested collections plus 20 inputs builds 78 MiB of collection-path vectors.
  - `hid-probe` then serialises everything to pretty JSON (several GB) and prints the descriptor. A buggy or malicious USB device can OOM the probe, and later the collector.
- **Fix:**
  - Put a global cap on the total number of fields (for example 16k) and on collection depth (for example 32), and return a `ParseError` when either is exceeded.
  - Store each collection path once (for example `Vec<Vec<Usage>>` plus an index, or `Arc<[Usage]>`) instead of copying it per field.
  - Rename `MAX_RANGE_EXPANSION`: it doesn't limit range expansion (see N1).

### R4 (medium): usage page is resolved when the Local item is read, not at the Main item (**verified**)
- **Where:** `crates/ups-hid/src/descriptor.rs:322-327`.
- **What:** A 1- or 2-byte Usage / Usage Min / Usage Max is combined with `globals.usage_page` *when the local item is read*. HID 1.11 §6.2.2.8 says the last declared Usage Page is concatenated with the usage *when the parser reaches the Main item*. I'm quoting that from memory, so treat the exact wording as unverified. Linux has done this since 2019 (`hid_concatenate_last_usage_page`). Linux only re-pages the trailing usages, back to the most recent usage that already carries the current page, so mixed-page local sets keep working.
- **Failure scenario (reproduced):** `05 01 09 30 05 84 … B1 02` is parsed as usage `0x0001:0x0030` (Generic Desktop X) instead of `0x0084:0x0030` (Voltage). The field name and any NUT mapping are then wrong. The same applies to collection usages and to Usage Min/Max. If the page changes between Min and Max, `resolved()` returns an empty list because `min.page != max.page`.
- **Fix:** store the declared size (or an "explicit page" flag) with each local usage. At the Main item, apply the Linux rule: walk the 16-bit usages backwards and give the current page to each one until you reach one that already has it. Add tests for "page after usage" and for "two pages in one local set". Eaton descriptors normally declare the page first, so this is a latent bug rather than a confirmed one for the 5E.

### R5 (medium): on Windows the "report descriptor" is a reconstruction, not the device's bytes
- **Where:** `apps/hid-probe/src/main.rs:217-221`, `docs/adr/0001-data-source.md:32-34`, `fixtures/README.md:5`.
- **What:** I verified this in `hidapi-2.6.7/etc/hidapi/windows/hid.c:1548-1557`: `hid_get_report_descriptor` on Windows calls `hid_winapi_descriptor_reconstruct_pp_data`. It rebuilds a descriptor from the HIDP preparsed data, and only for the opened top-level collection.
  - The rebuilt descriptor is logically equivalent but not byte-identical. Item order, padding, how globals are emitted, string/designator items, delimiters and vendor collections in other TLCs can all differ.
  - On Linux, hidraw returns the real descriptor for the whole interface.
- **Failure scenario:** fixtures captured on Windows are stored as `report_descriptor_hex`. The ADR calls them "the source of truth", but they don't match what NUT/libusb or the Raspberry Pi (M4) will see. A parser bug that depends on byte order (for example R4) can pass on the Windows fixture and fail on the Pi, or the other way round.
- **Fix:** record the provenance in the dump, for example `"descriptor_source": "windows-reconstructed" | "hidraw"` or the OS name. Note the caveat in ADR-0001 and `fixtures/README.md`. If possible, also capture the raw descriptor once on Linux (`/sys/class/hidraw/hidrawN/device/report_descriptor`) or with a USB analyser.

## Low

### R6 (low): array fields are flattened and labelled with the first usage (**verified**)
- **Where:** `crates/ups-hid/src/descriptor.rs:359-366`. Doc gap at `Field`, `:37-60`.
- **What:** For an Array main item (flag bit 1 = 0), each of the `report_count` slots holds a *selector/index* into the usage list, offset by `logical_min`. The parser emits one `Field` per slot, all labelled with `usages.first()`. `extract()` returns the index, not a value of that usage.
- **Failure scenario (reproduced):** Usage Min 0x10 / Max 0x12, count 2, `81 00` gives two fields both named `PowerDevice.BatterySystem`. A selector value of 2 then looks like "BatterySystem = 2", when it actually means usage 0x12 (Battery) is active.
- **Fix:** model arrays explicitly. One option is a `usages: Vec<Usage>` / `is_array` on the field, plus a helper that maps an index to a usage. Another is to name array slots `Array[n]` in the probe. At minimum, document the behaviour on `Field` and in `hid-probe` output.

### R7 (low): mixing Usage and Usage Min/Max in one local set loses the range (**verified**)
- **Where:** `crates/ups-hid/src/descriptor.rs:185-195`.
- **What:** If any explicit `Usage` exists, `resolved()` ignores Usage Min/Max entirely. HID 1.11 builds one ordered list from both.
- **Failure scenario (reproduced):** `09 01 19 10 29 12`, then 4 variable fields, gives usages `[01, 01, 01, 01]`. The expected result is `[01, 10, 11, 12]`.
- **Fix:** keep an ordered `Vec<LocalUsage>` where each entry is either a single usage or a range, and expand them in declaration order. Rare in UPS descriptors, so low priority, but cheap to fix with R4.

### R8 (low): a nibble-sized Unit Exponent is only decoded as a nibble when it is 1 byte long (**verified**)
- **Where:** `crates/ups-hid/src/descriptor.rs:295-307`.
- **What:** `56 0E 00` (2-byte item, value 0x000E) yields `unit_exponent = 14` instead of −2. Linux treats any value with `raw & ~0xF == 0` as a 4-bit two's-complement nibble, whatever the item size. `signed as i8` also silently truncates 2- and 4-byte values.
- **Fix:** `if unsigned & !0xF == 0 { nibble } else { i8::try_from(signed).unwrap_or(0) }`, or clamp the value. Add tests for `55 0E` (−2, already correct), `56 0E 00` and `55 FE`.

### R9 (low): string-index usages silently produce nothing on Linux
- **Where:** `apps/hid-probe/src/main.rs:327-330`.
- **What:** On Linux, `hidapi`'s hidraw backend does not implement `hid_get_indexed_string`: it always returns −1 with "not supported by hidraw" (`linux/hid.c:1327-1336`, verified). `.ok().flatten()` swallows that error, so on Linux every `iManufacturer`/`iProduct`/`iDeviceChemistry` string comes out as `None` with no hint why. The M4 plan to run this on a Raspberry Pi makes this relevant.
- **Fix:** record the error, for example `string_error: Option<String>`, or print a one-time note. Alternatively, on Linux read the strings via libusb or sysfs.

### R10 (low): `ALARM` is a real `ups.status` token but is treated as unknown
- **Where:** `crates/ups-model/src/status.rs:4-54`. The test at `:110-114` asserts that `ALARM` is unknown.
- **What:** The NUT developer guide ("Status data") lists 14 tokens, and the code matches all of them. The guide also says the framework adds `ALARM` to `ups.status` automatically whenever `alarm_set()` is used (`ups.alarm` non-empty). Any NUT source (M4) will therefore routinely deliver `OL ALARM`, which `from_nut` reports as "unknown".
- **Fix:** add `const ALARM` and the token, and update the test. Doc nits on the existing flags:
  - `OFF` means "not supplying power to the load", not just "output off".
  - `CAL` is runtime calibration (on battery).
  - `FSD` is injected by `upsd` on command from the primary `upsmon` and is normally not set by drivers.

### R11 (low): the snapshot JSON doesn't use the NUT names the crate docs promise
- **Where:** `crates/ups-model/src/lib.rs:4-6` ("the same names are used everywhere — in storage, the API and the UI") against `crates/ups-model/src/snapshot.rs:17-32`.
- **What:** serde serialises `battery_charge_pct`, `load_pct` and so on, not `battery.charge` or `ups.load`. `vars.rs` defines NUT names that `Snapshot` never uses. `UpsStatus` serialises through bitflags as `"OL | CHRG"`, which is neither a NUT string nor stable if a constant is renamed.
- **Fix:** either add `#[serde(rename = "battery.charge")]` (and so on) plus a custom `UpsStatus` (de)serialiser that uses `to_nut`/`from_nut`, or soften the crate doc. Pin the chosen wire format with a golden-JSON test before storage (M1) depends on it.

### R12 (low): `Snapshot.status` can't express "unknown"
- **Where:** `crates/ups-model/src/snapshot.rs:16`, `:44`.
- **What:** Every measurement is `Option` ("never invent data"), but `status` is a bare `UpsStatus`. `Snapshot::empty` sets it to no flags. "Status not read or stale" can't be told apart from "status read and empty". A real UPS always reports at least OL, OB or OFF, but a stale or failed read would look like a valid, all-clear status to the outage engine (M2).
- **Fix:** make it `Option<UpsStatus>`, or add an explicit staleness flag (NUT has the "data stale" concept).

### R13 (low): CI doesn't test what the manifest claims, and isn't reproducible
- **Where:** `.github/workflows/ci.yml`, `rust-toolchain.toml:2`, `Cargo.toml:8`.
- **What:**
  - **MSRV untested:** `rust-version = "1.88"` is never tested. Dependencies are fine (highest is clap at 1.85, verified), but nothing stops code from using >1.88 APIs.
  - **Floating toolchain:** `channel = "stable"` floats, and with `-D warnings` any new clippy lint in a future stable release will turn CI red on an unrelated PR.
  - **No docs check:** CI doesn't build docs with `-D warnings` (it is clean today).
  - **Workflow hardening:** no `permissions: contents: read`, no `concurrency` group, and the actions are pinned to major tags only (`actions/checkout@v4`).
- **Will it pass?** Yes, for ubuntu-latest and windows-latest as written. `libudev-dev` is installed for the default `linux-static-hidraw` feature, `pkg-config` and the C compiler come with the runner image, and MSVC is on windows-latest. I couldn't run the workflow itself.
- **Fix:** pin `channel = "1.99"` (bump on purpose), add an MSRV job (`dtolnay/rust-toolchain@1.88` running `cargo check --workspace --all-targets`), add a `cargo doc --no-deps` step with `RUSTDOCFLAGS=-D warnings`, and add `permissions:` / `concurrency:`.

### R14 (low): the lint configuration doesn't match the code's `allow`s
- **Where:** `Cargo.toml:29-34`, and allows at `descriptor.rs:28,92,103,206-210` and `usages.rs:59,143`.
- **What:** Only `clippy::all` is enabled. `cast_possible_truncation`, `cast_sign_loss`, `cast_possible_wrap`, `cast_precision_loss` and `too_many_lines` are pedantic lints, so these `#[allow]`s are dead. The `#[must_use]` attributes also suggest that pedantic was intended. Meanwhile the casts that matter go unlinted, for example `unsigned as u16` / `signed as i8` in the parser and `raw as f64` in `main.rs:393`.
- **Fix:** add `pedantic = { level = "warn", priority = -1 }` (plus whatever targeted allows you want) and fix what it reports, or remove the dead allows.

### R15 (low): feature report buffer and payload length ignore the descriptor
- **Where:** `apps/hid-probe/src/main.rs:251-255` and `:283`.
- **What:**
  - Fixed 256-byte buffers are used for both feature and input reports. A report longer than 255 bytes is truncated without notice. That's unlikely for UPSes, but the descriptor already gives the exact size (`report_len`).
  - **Uncertain:** on Windows, `IOCTL_HID_GET_FEATURE` may return the TLC's maximum `FeatureReportByteLength` rather than the specific report's length. Then `payload_hex` would carry trailing bytes that aren't part of the report. Field decoding is unaffected because it is offset-based. I couldn't verify this without hardware.
- **Fix:** allocate `report_len(kind, id) + 1` bytes (or the maximum over all reports for input), and trim `payload` to `report_len`. Record a warning when `n - 1 != report_len`, which is useful evidence for fixtures.

### R16 (low): unit exponent output is misleading for SI-linear (CGS) units
- **Where:** `apps/hid-probe/src/main.rs:399-402`, `crates/ups-hid/src/units.rs`.
- **What:** HID "SI Linear" uses cm and g. Volts are therefore declared as unit `0x00F0D121` with exponent 7, which means plain volts. The probe prints `230 V e7`, which reads as 2.3 × 10⁹ V. The same happens for W/VA. The code comments correctly say the exponent isn't applied, but the output is easy to misread when curating fixtures.
- **Fix:** in `units`, provide a normalised exponent for SI units, `unit_exponent − 7` for V and W, and print that instead, for example `V ×10^0`. Alternatively print `exp=7 (CGS)`.

### R17 (low): dump files can overwrite each other (**verified by reading the code**)
- **Where:** `apps/hid-probe/src/main.rs:413-419`.
- **What:** The file name is `{vid}-{pid}-{YYYYmmddTHHMMSSZ}.json`, at one-second resolution. Several targets with the same VID:PID are common. With `--vid/--pid`, every TLC of the device is a target, including vendor and keyboard-style collections. On Linux, hidapi lists each TLC of one hidraw node as a separate entry. Targets that fail to open or to read the descriptor return immediately, as does any run with `--listen 0`. They then get the same timestamp, and the later dump silently replaces the earlier one.
- **Fix:** include the interface number and usage page/usage (or a running index) in the name, and open the file with `create_new`.

### R18 (low): one failed write aborts the remaining devices, and Ctrl-C loses everything
- **Where:** `apps/hid-probe/src/main.rs:129-134`, `:284-314`.
- **What:** `write_dump(...)?` returns from `main` on the first I/O error, so later targets are never probed. Output is only written after listening ends, so interrupting a long `--listen` run discards the descriptor and feature reports that were already read.
- **Fix:** report the error and continue with the next target. Write the descriptor and feature part before listening, or handle Ctrl-C.

### R19 (low): the read-only guard is lint-only and hidapi-only
- **Where:** `clippy.toml`, `Cargo.toml:31-32`, ADR-0001 §Decision 4.
- **What (verified as effective):** clippy denies direct calls, function paths and typed function pointers for all three methods. `hidapi::ffi` and the backend traits are private, and `unsafe_code = "forbid"` blocks raw FFI.
  - The remaining gaps are that `cargo build` and `cargo run` don't enforce it, and a future dependency with a safe write API (for example `rusb`/`nusb` control transfers, or another HID crate) isn't covered.
  - On Windows, hidapi opens the handle with `GENERIC_READ | GENERIC_WRITE` (`windows/hid.c:346`), so the OS doesn't enforce read-only either. That is expected and has no effect on the device, but the ADR should say that the guarantee is code-level only.
- **Fix:** add a `cargo deny` `bans` entry, or a CI grep, for other USB/HID crates. Mention the scope of the guard in ADR-0001. Optionally wrap `HidDevice` in a newtype that exposes only the read methods, and disallow `hidapi::HidApi::open*` outside that module.

### R20 (low): `ParseError` docs promise more than the parser checks
- **Where:** `crates/ups-hid/src/descriptor.rs:203-205`, `:275-279`.
- **What:** The doc says the parser rejects "unbalanced collections". It only rejects an extra End Collection. A descriptor with unclosed collections parses `Ok` (verified with `05 84 09 04 A1 01`). Being lenient is reasonable, but the doc is wrong.
- **Fix:** either return `UnbalancedCollection` when `path` isn't empty at the end, or reword the doc.

### R21 (low): README and ADR accuracy
- `README.md:37-48`: no Linux prerequisites. Linux needs `libudev-dev` and `pkg-config` to build, which CI already installs. It also needs read access to `/dev/hidraw*` (a udev rule) to probe, otherwise every target reports `OPEN FAILED: Permission denied`.
- `crates/ups-model/src/vars.rs:3`: the link `…/developer-guide.chunked/new-names.html` returns **HTTP 404** (verified). The current page is `https://networkupstools.org/docs/user-manual.chunked/nut-names.html`, which points to RFC 9271 for the variable list.
- `docs/adr/0001-data-source.md:13-15`: "NUT does have a native Windows HID backend, but it is experimental and read-only". **Unverified**: I couldn't confirm this, so please cite a source or rephrase.

### R22 (low): tests are missing for the important edge cases
- **What:** The suite covers the happy path well. Nothing covers:
  - long items, which were checked and work;
  - 4-byte extended usages, which work;
  - Usage Min/Max expansion, the "more fields than usages" rule and mixed usage sets (R7);
  - usage page after usage (R4);
  - arrays (R6);
  - one report ID shared across Input/Feature (separate counters, which were checked and work);
  - unaligned multi-byte fields (12 bits at offset 4 works) and full-width 32-bit signed fields (work);
  - negative unit-exponent encodings (R8), a negative physical range, `bit_size` 0 or more than 32;
  - hostile input (R2, R3).

  `hid-probe` has no tests at all (`parse_hex_u16`, `is_target`, `field_name`, redaction R1). `ups-model` has no golden-JSON test for the wire format (R11).
- **Fix:** add these as unit tests (I used the byte strings quoted in this report), plus a "never panics" property or fuzz test.

## Nits

### N1 (nit): `MAX_RANGE_EXPANSION` is misnamed, and `resolved()` always expands in full
- **Where:** `descriptor.rs:198`, `:185-195`, `:269-273`.
- **What:** The constant caps `report_count`, not range expansion. `resolved()` builds up to 65,536 usages for every main item, including Collections, which only use `.first()`. Fields beyond 4,096 per item are dropped silently, while the `fields` doc says "all non-constant fields".
- **Fix:** rename it (for example `MAX_FIELDS_PER_ITEM`) and compute only what is needed.

### N2 (nit): Delimiter items are ignored
- **Where:** `descriptor.rs:332`.
- **What:** Alternative usages in a delimited set are appended as if they were sequential usages. Linux keeps only the first usage of each set.
- **Fix:** honour delimiter open/close (tag 0xA). This is rare in UPSes.

### N3 (nit): `ReportDescriptor` allows inconsistent states
- **Where:** `descriptor.rs:129-137`.
- **What:** It derives `Default` and has public `fields`, but private `report_bits`, so a hand-built value reports `report_len == 0` for its own fields. The private `report_bits` is also skipped by serde, so `report_len` isn't in the JSON dump.
- **Fix:** make the fields private with accessors, or serialise the report lengths.

### N4 (nit): `parse_hex_u16` strips repeated prefixes
- **Where:** `main.rs:48-51`.
- **What:** `trim_start_matches` removes repeated prefixes, so `0x0x12` and `+12` are accepted.
- **Fix:** use `strip_prefix`.

### N5 (nit): `field_name` mixes naming styles
- **Where:** `main.rs:349-358`.
- **What:** Collection parts are bare names (`PowerSummary`), but the leaf is `BatterySystem.RemainingCapacity`, so a full name reads `PowerSummary/BatterySystem.RemainingCapacity`.
- **Fix:** use NUT's `UPS.PowerSummary.RemainingCapacity` style, so the output can be compared directly with NUT `-DD` logs and mge-hid tables.

### N6 (nit): `.gitattributes` has no trailing newline and forces LF everywhere
- **What:** The file has no trailing newline. `* text=auto eol=lf` also forces LF for future `.bat`/`.cmd` files.
- **Fix:** add `*.bat text eol=crlf` / `*.cmd text eol=crlf`, and add `*.bin binary` for any raw descriptor dumps.

### N7 (nit): `.gitignore` ignores every `*.db`/`*.sqlite`
- **What:** This would also hide curated database fixtures under `fixtures/`.
- **Fix:** anchor these patterns, or add a `!fixtures/**` exception, when needed.

### N8 (nit): `Snapshot::estimated_load_w` assumes `ups.load` is a percentage of real power
- **What:** It assumes `ups.load` is relative to *real* power. Some devices report load relative to VA. The doc already says "estimated". Also, `vars::UPS_POWER_NOMINAL` exists but `Snapshot` has no VA-nominal field.
- **Fix:** confirm this on the 5E capture and document which nominal value it uses.

## Checked and found correct

- **Short item sizes:** the 0/1/2/4-byte encoding, including `bSize = 3` meaning 4 bytes.
- **Long items:** the `0xFE` prefix and size, with truncation detected.
- **Truncation:** detected for every item size.
- **Push/Pop:** restores globals, including the report ID, and detects underflow.
- **Item types:** main, global and local tags are all mapped correctly.
- **Locals:** reset after every main item.
- **Extended usages:** 4-byte usages are split correctly.
- **Variable fields with more fields than usages:** the extra fields reuse the last usage.
- **Bit offsets:** tracked separately per (kind, report ID). Fields declared before the first Report ID get ID 0.
- **Logical/physical maximum quirk:** a 1-byte `0xFF` maximum is read unsigned when the minimum is ≥ 0, and this is decided at field time, which is more robust than Linux's item-time decision.
- **Two's-complement extraction:** correct for 1 to 32 bits, including unaligned fields. Short data returns `None`.
- **`scale()`:** handles undefined (0/0) and identity physical ranges, and its i64 spans cannot overflow.
- **hid-probe report-ID handling:** correct on both OSes per hidapi's contract (feature: data from `buf[1]`, return value includes the ID byte; input: an ID byte only when the device uses IDs, because Windows strips the 0 byte, `windows/hid.c:1206-1214`).
- **hid-probe descriptor buffer:** 4096 bytes, which equals `HID_API_MAX_REPORT_DESCRIPTOR_SIZE`.
- **Writes to the device:** none. hid-probe uses only the read paths (`get_report_descriptor`, `get_feature_report`, `read_timeout` and `get_indexed_string`, which is a GET_DESCRIPTOR request). `HidD_SetNumInputBuffers` on open only affects the host.
- **Usage tables:** the Power Device and Battery System names and the string-index usages match the HID Power Device usage table as mirrored in NUT's `usbhid-ups` lookup table.
- **Unit codes:** V, A, W/VA, s, K, Hz and A·s nibbles are correct.
- **NUT tokens:** the 14 tokens match the NUT developer guide (but see R10 for ALARM). The `vars.rs` names are all standard NUT names.
- **serde:** `Option` fields tolerate missing keys, and `extra` is defaulted and skipped when empty.
- **Workspace:** `resolver = "3"`, `unsafe_code = "forbid"`, release profile and committed `Cargo.lock` are all appropriate. Build, test, clippy, fmt and doc are all clean on 1.99.1.
